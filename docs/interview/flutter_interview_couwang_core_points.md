# Flutter 실무 면접 핵심 정리

이 문서는 **쿠왕 프로젝트를 기준으로 실제로 말할 수 있는 내용**과,  
**쿠왕에 직접 없는 기술은 실무 면접 답변용 일반 정리**를 함께 묶은 면접 대비 문서다.

면접에서는 아래 순서로 답하면 안정적이다.

1. 개념을 짧게 설명한다.
2. 쿠왕에서 어떻게 적용했는지 말한다.
3. 왜 그렇게 선택했는지 근거를 덧붙인다.
4. 한계나 대안까지 말하면 실무형 답변이 된다.

## 1. Widget / Stateless / Stateful

### 핵심 개념
- Flutter UI는 거의 모든 것이 Widget이다.
- `StatelessWidget`은 외부 입력이 바뀔 때만 다시 그려지는 정적인 UI에 적합하다.
- `StatefulWidget`은 사용자 입력, 로딩 상태, 선택 상태처럼 내부 상태 변화가 있는 화면에 적합하다.

### 쿠왕 사례
- `StatelessWidget`
  - 버튼, 카드, 빈 상태 UI, 배지 같은 반복 UI 조각에 많이 사용했다.
  - 예: `EmptyStateMascot`, `CouponCard`, `MembershipCard`
- `StatefulWidget`
  - 쿠폰 등록 화면, 홈 화면, 설정 화면처럼 상태 변화가 많은 곳에 사용했다.
  - 예: `CouponCreateScreen`, `HomeDashboardScreen`, `SettingsScreen`

### 면접 답변 포인트
> Flutter에서는 화면도 Widget이고, 작은 UI 조각도 Widget입니다.  
> 쿠왕에서는 재사용 가능한 표시용 컴포넌트는 `StatelessWidget`으로 두고,  
> OCR 처리 상태, 검색어, 필터, 권한 상태처럼 화면 내부 상태가 바뀌는 곳은 `StatefulWidget`으로 분리했습니다.

### 꼬리질문 대비
- “무조건 Stateful이 나쁜 건 아니냐”  
  -> 아니다. 상태 범위가 화면 내부에 한정되고 복잡도가 낮으면 `setState` 기반이 가장 단순하고 유지보수에 유리하다.

## 2. build / initState / dispose

### 핵심 개념
- `build`: 현재 상태를 기준으로 UI를 다시 그린다.
- `initState`: 위젯이 처음 만들어질 때 1회성 초기화를 한다.
- `dispose`: 컨트롤러, 리스너, 스트림, 타이머 같은 리소스를 정리한다.

### 쿠왕 사례
- `initState`
  - 쿠폰 수정 화면에서 기존 값을 폼에 채우는 작업
  - 설정 화면에서 버전 정보와 자동 감지 설정 로드
  - 앱 시작 시 알림 payload 후처리 준비
- `build`
  - 검색어, 정렬, 필터 상태를 기준으로 홈 리스트를 다시 그림
  - 알림 권한 상태에 따라 설정 토글 표시가 달라짐
- `dispose`
  - `TextEditingController`, `Timer`, `WidgetsBindingObserver` 제거
  - 갤러리 스캔 관련 리소스 정리

### 면접 답변 포인트
> 쿠왕에서는 `initState`를 “초기값 주입과 초기 로딩” 용도로 썼고,  
> `build`는 항상 현재 상태만 반영하도록 유지했습니다.  
> `dispose`에서는 텍스트 컨트롤러, 타이머, observer를 꼭 정리해서 메모리 누수나 중복 리스너를 막았습니다.

### 주의할 말
- `build` 안에서 API 호출이나 DB 저장 같은 부수효과는 피하는 게 좋다.

## 3. setState / Provider

### 핵심 개념
- `setState`는 해당 위젯 내부 상태가 바뀌었음을 Flutter에 알리는 가장 기본적인 방법이다.
- `Provider`는 상태를 여러 화면/위젯 트리에 걸쳐 공유할 때 유용한 패턴이다.

### 쿠왕 사례
- 쿠왕은 **상태관리 라이브러리 없이 `setState` 중심**으로 구현했다.
- 이유:
  - 앱 규모가 아직 MVP 수준이었고
  - 상태 대부분이 특정 화면 내부에 머물렀고
  - 로컬 DB와 repository가 사실상 데이터 소스 역할을 했기 때문이다.

### 면접 답변 포인트
> 쿠왕에서는 `setState`를 선택했습니다.  
> 화면별 상태 범위가 비교적 명확했고, 전역 상태보다 로컬 화면 상태가 많았기 때문입니다.  
> 대신 데이터 원본은 repository로 분리해서 UI와 저장 로직을 섞지 않았습니다.  
> 추후 화면 간 공유 상태가 더 많아지면 `Provider`나 `Riverpod`로 옮길 수 있는 구조를 염두에 두고 repository 계층은 유지했습니다.

### Provider 관련 일반 답변
> `Provider`는 단순 전역 변수보다 의존성 주입과 상태 변경 추적이 명확해서 중간 규모 앱에서 많이 씁니다.  
> 다만 작은 앱에서 너무 이르게 도입하면 오히려 구조가 무거워질 수 있어서, 상태 범위와 팀 규모를 보고 결정하는 편입니다.

## 4. async/await / Future

### 핵심 개념
- Flutter에서 파일 읽기, DB 접근, 권한 요청, OCR, 알림 예약은 대부분 비동기다.
- `Future`는 미래에 완료될 작업을 뜻하고, `async/await`는 그 흐름을 읽기 쉽게 만든다.

### 쿠왕 사례
- OCR 처리
  - 이미지 선택 -> 바코드 인식 -> 텍스트 인식 -> 자동 입력 결과 생성
- DB 처리
  - 앱 시작 시 `initialize()`
  - 저장/삭제 시 `await` 기반 순차 처리
- 권한 처리
  - 사진 권한, 알림 권한 요청
- 갤러리 자동 감지
  - 최근 이미지 조회 -> 후보 분석 -> 중복 판별

### 면접 답변 포인트
> 쿠왕은 비동기 작업이 많은 앱이었습니다.  
> 이미지 OCR, 로컬 DB, 권한 요청, 알림 예약이 모두 `Future` 기반이어서,  
> `async/await`로 순서를 분명하게 유지했습니다.  
> 특히 저장 로직에서는 DB 저장과 후처리를 분리해서, 후처리 실패가 전체 저장 실패처럼 보이지 않도록 구성했습니다.

### 꼬리질문 대비
- “then 대신 await를 쓴 이유”  
  -> 비동기 흐름이 길어질수록 `await`가 가독성과 예외 처리에 유리했다.

## 5. Navigator

### 핵심 개념
- Flutter에서 화면 이동은 `Navigator`가 관리한다.
- `push`, `pop`, `pushNamed`, `pushNamedAndRemoveUntil` 등을 상황에 맞게 쓴다.

### 쿠왕 사례
- 라우트 문자열은 `AppRouter`로 모아 관리했다.
- 하단 탭은 단순 push가 아니라 **루트를 교체하는 방식**으로 정리했다.
- 알림 탭 진입 시에는
  - 홈으로 스택을 정리한 뒤
  - 쿠폰 상세를 push 하는 흐름을 썼다.
- 삭제 후에는 화면 스택이 꼬이지 않도록 홈으로 복귀하게 정리했다.

### 면접 답변 포인트
> 쿠왕에서는 `Navigator`를 단순 화면 이동이 아니라 “화면 스택 관리” 관점으로 다뤘습니다.  
> 예를 들어 하단 탭은 push 누적이 아니라 `pushAndRemoveUntil`로 현재 루트를 교체했고,  
> 알림 탭 진입 시에도 홈을 먼저 기준 화면으로 맞춘 뒤 상세로 이동하게 해서 뒤로가기 흐름을 예측 가능하게 만들었습니다.

## 6. API 연동 흐름

### 쿠왕 기준
- **쿠왕은 외부 REST API 중심 앱이 아니다.**
- 현재는 서버 없이 로컬 저장 기반으로 동작한다.
- Firebase Analytics / Crashlytics는 사용하지만, 일반적인 “비즈니스 API 연동”과는 다르다.

### 실무 면접용 일반 답변
> API 연동은 보통 `service -> model parsing -> repository or state layer -> UI` 흐름으로 설계합니다.  
> 화면에서 직접 HTTP를 호출하지 않고, 서비스 계층에서 응답을 받고 모델로 변환한 뒤,  
> repository나 상태관리 계층을 통해 UI에 전달하는 구조를 선호합니다.  
> 또한 로딩, 성공, 빈 데이터, 실패를 구분해서 처리하고, 예외 메시지를 사용자 메시지와 내부 로그로 나누는 편입니다.

### 추가로 말하면 좋은 포인트
- DTO와 UI 모델 분리
- timeout / retry / error mapping
- 토큰 갱신 / 인증 실패 처리
- 캐싱 전략

## 7. SQLite / 로컬 저장

### 핵심 개념
- 네트워크 없는 환경에서도 동작해야 하거나, 사용자 개인 데이터를 기기 안에 저장해야 할 때 로컬 DB가 유용하다.
- Flutter에서는 `sqflite`를 많이 쓴다.

### 쿠왕 사례
- 쿠왕은 서버 없는 앱이라 핵심 데이터를 전부 로컬에 저장했다.
- 저장 대상:
  - 쿠폰
  - 멤버십
  - 알림 설정
  - 알림 로그
  - 이미지 자산 메타데이터
- 이미지 바이너리를 DB에 그대로 넣지 않고,
  - 파일은 앱 전용 디렉터리에 저장
  - DB에는 경로와 메타데이터만 저장했다.

### 면접 답변 포인트
> 쿠왕은 서버 없이 동작하는 구조라 SQLite를 핵심 저장소로 사용했습니다.  
> 쿠폰, 멤버십, 알림 설정, 알림 로그를 로컬 DB에 저장했고,  
> 이미지는 DB에 바로 넣지 않고 파일 시스템에 저장한 뒤 경로만 관리했습니다.  
> 이렇게 분리하면 DB가 비대해지는 걸 줄이고 이미지 교체나 삭제도 더 명확하게 관리할 수 있습니다.

### 꼬리질문 대비
- “SharedPreferences 대신 SQLite를 쓴 이유”  
  -> 단순 키값 저장을 넘어서 리스트/상세/정렬/관계가 있는 데이터 구조가 필요했기 때문.

## 8. MethodChannel / 네이티브 연동

### 핵심 개념
- Flutter에서 직접 알 수 없는 플랫폼 고유 정보를 가져오거나 네이티브 기능을 호출할 때 `MethodChannel`을 사용한다.

### 쿠왕 사례
- `AppPermissionService`에서 Android SDK 버전을 확인할 때 `MethodChannel`을 사용했다.
- 이유:
  - Android 13 이상과 이하에서 알림 권한 동작이 다르기 때문
  - 런타임에서 기기 SDK를 정확히 확인해 분기하기 위해서

### 면접 답변 포인트
> 쿠왕에서는 `MethodChannel`을 Android SDK 버전 확인에 사용했습니다.  
> Android 13 이상은 알림 런타임 권한을 요청해야 하지만, 그 아래 버전은 앱 내부 동의 흐름으로 처리해야 했기 때문입니다.  
> Flutter 단에서 단순 추정하지 않고 네이티브 값을 받아와 권한 UX를 분기했습니다.

### 꼬리질문 대비
- “언제 MethodChannel을 쓰는가”  
  -> Flutter 패키지로 해결되지 않거나, 플랫폼 고유 값을 직접 받아야 할 때.

## 9. 성능 최적화 포인트

### 쿠왕 사례 기준으로 말할 수 있는 포인트
- OCR/바코드 처리는 모두 비동기로 분리
- 갤러리 자동 감지는
  - 최근 30일
  - 최대 50장
  - 하루 최대 5회  
  같은 제한을 둬서 과도한 스캔을 막음
- 이미 처리한 이미지는 해시로 기억해 중복 분석을 줄임
- 제목 OCR은 상단 12% 영역 제외, 최대 2줄 제한으로 불필요한 후보를 줄임
- 알림 재예약과 저장 후처리는 저장 성공과 분리해서 UX 지연을 줄임

### 면접 답변 포인트
> 쿠왕에서는 이미지 OCR과 갤러리 자동 감지가 비용이 큰 작업이라,  
> 스캔 범위를 최근 이미지와 일일 횟수로 제한하고, 이미 처리한 이미지는 해시로 재분석을 막았습니다.  
> 또 저장 흐름에서는 DB 저장 성공과 후처리를 분리해서 사용자가 저장 실패처럼 느끼지 않도록 했습니다.

### 일반론으로 덧붙이면 좋은 것
- 불필요한 rebuild 줄이기
- 큰 리스트는 `ListView.builder`
- 이미지 사이즈 제한
- 계산량 큰 작업은 isolate 또는 네이티브/플러그인 활용 검토

## 10. 스토어 배포 흐름

### 쿠왕 사례
- Android
  - 버전 관리: `pubspec.yaml`
  - `flutter analyze`
  - `flutter build appbundle --release`
  - Play Console 업로드
  - 권한 정책, 스토어 문구, 출시노트 점검
- iOS
  - `flutter analyze`
  - `flutter build ipa --release`
  - Xcode/Transporter/App Store Connect 업로드
  - 개인정보 라벨, 심사 메모, 권한 설명, 수출 규정 확인

### 면접 답변 포인트
> 쿠왕은 Flutter 기반이지만 실제 배포 단계에서는 플랫폼별 체크 포인트가 달랐습니다.  
> Android는 AAB 생성과 Play Console 권한 정책 대응이 중요했고,  
> iOS는 IPA 생성 이후 App Store Connect 심사 항목, 개인정보 라벨, 권한 문구, 알림/화면 방향 같은 정책 요소를 함께 확인해야 했습니다.  
> 그래서 빌드만 성공하는 것이 아니라, 스토어 제출 문서와 정책 대응까지 포함해 배포 흐름을 관리했습니다.

### 꼬리질문 대비
- “Flutter인데 왜 플랫폼별 배포 차이가 있나”  
  -> 앱 코드는 공유돼도 심사 정책, 서명, 권한, 스토어 메타데이터는 플랫폼별로 다르기 때문.

## 면접에서 자주 나오는 보조 질문

### Q. 쿠왕에서 가장 어려웠던 기술 이슈는?
추천 답변:
> 갤러리 자동 감지와 OCR 정확도 개선이 가장 어려웠습니다.  
> 단순히 텍스트를 읽는 수준이 아니라, 상태바 텍스트나 헤더 문구를 제외하고 실제 쿠폰명과 유효기간만 추출해야 했기 때문입니다.  
> 그래서 상단 영역 제외, 날짜 파서 보강, 중복 감지 로직을 같이 다듬었습니다.

### Q. 쿠왕에서 아쉬운 점은?
추천 답변:
> 현재는 `setState` 중심 구조라 화면 간 상태 공유가 더 많아지면 상태관리 계층을 보강할 필요가 있습니다.  
> 또 서버 동기화나 백업 기능이 없어서, 향후에는 로그인/클라우드 연동 구조를 검토할 수 있습니다.

### Q. 쿠왕에서 잘한 설계 포인트는?
추천 답변:
> 로컬 DB, 이미지 파일 저장, 알림 서비스, 권한 서비스, repository를 분리해서  
> UI와 저장/플랫폼 로직을 최대한 나눠둔 점입니다.  
> 그래서 기능이 추가돼도 한 화면에서 모든 걸 처리하지 않고 책임을 분산할 수 있었습니다.

## 빠른 암기 포인트

- 쿠왕은 **Flutter + 로컬 저장 중심 앱**
- 상태관리는 **`setState` + repository 구조**
- 데이터 저장은 **SQLite + 파일 시스템 분리**
- 권한은 **앱 내부 안내 + 시스템 권한 요청 흐름**
- 알림은 **로컬 예약 + 로그 저장 + 탭 라우팅 처리**
- OCR은 **온디바이스 분석 + 후처리 규칙 보강**
- 배포는 **빌드 + 스토어 정책 대응까지 포함**
